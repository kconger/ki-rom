# The R4600 — expectations and the first oracle

The suite selects its expectations by `PRId`. The R4400 and the R5000 have both
run it on real Indys and pass every check (`oracle/`). An R4600 first ran it on
2026-11-01, on a Killer Instinct board (A-19489, PRId `0x2020`, FIR `0x2020`,
Config `0x000264B3`), from the KI test ROM. This file says where each R4600
answer comes from, so that a failure on an R4600 can be weighed properly.

## Measured on the KI board

That run failed 37 checks in 7 tests. One cause was a bug in the test, three
were the R4600 differing from both the R4400 and the R5000:

| tests | what the R4600 does | now expected |
|---|---|---|
| `umode/load_miss_third`, `umode/kseg0_load_third` (irix5 only) | **test bug:** the User code logged its address with `sd`, a Reserved Instruction with UX clear, so every later record shifted by one | the code uses `sw`; every CPU |
| `umode/kseg0_load_first`, `_third` (irix5 only) | BadVAddr for a User load from `0xFFFFFFFF80000000` with UX clear reads `0x3FFFFF0080000000`; low 32 bits right, not sign-extended. With UX set it is sign-extended | that value, on the R4600 with UX clear |
| `fpu/compare_nan`, `fpu/cmp_signalling_qnan`, `fpu/cmp_trap_on_signal` | Invalid only for the signalling predicates (cond 8-15), for `0x7FC00000` as for `0x7FA00000` — the manual's pseudocode exactly. So with Invalid enabled, `c.olt` on that NaN does not trap and stores false | on the R4600 |
| `fpu/vec_cvt_from_l` | `cvt.s.l` / `cvt.d.l` past 2^53 convert in hardware: no Unimplemented Operation trap | on the R4600, the rounded results and flags in the table; the values themselves are not measured yet |

The run also measured how the KI board itself treats an uncached store
narrower than 64 bits to SRAM or DRAM: it rewrites the whole doubleword, and the
other bytes read back as 0. The harness writes its status and log with whole
doublewords because of it (see `harness/ki_cputest.h`). Tests that make such
stores to memory would see it too; none failed for that reason.

The reason the case exists at all is the `sgiindy_MiSTer` FPGA core, which
presents itself as an R4600 (PRId/FIR `0x2020`): IRIX 5.3 hard-codes a 32-byte
data-cache line for imp 0x20 and a 16-byte one for the R4400, so that core
cannot pose as an R4400. Before this case existed, `identify()` refused imp 0x20
with rc=127.

## What the suite does not cover on an R4600

Things a real R4600 differs in that no test here looks at, so a pass says
nothing about them:

- **No Watch registers** (WatchLo/WatchHi, the Watch exception), no secondary
  cache (Config.SC = 1) and so no cache-error or VCE exceptions.
- **The cache organisation beyond correctness.** `cache/set_conflict` checks
  that a set conflict never returns the wrong line, not how many ways hold a
  line. A direct-mapped cache that reports R4600 geometry passes — which is
  exactly what the `sgiindy_MiSTer` core has.
- Anything about `Config.EC` / the clock ratio, which the PROM reads per CPU
  family.

## Still open after the first R4600 run

1. `mem/lwr_all_offsets` passed, so the R4600 gave one of the two known
   answers; the log line says which, but the ROM does not show a passing
   test's notes. Gate it once that line has been read.
2. `fpu/vec_cvt_from_l` past 2^53: the second run passed the rounded values
   and flags in the table.
3. How far the BadVAddr rule reaches. `umode/kernel_addr_badvaddr` takes the
   same upper half, `0x3FFFFF00`, as its guess for every other way a 32-bit
   User or Supervisor program reaches an address with bit 31 set: loads from
   KSEG1, KSEG2 and KSEG3, a store to KSEG0, a jump into KSEG0, and a
   Supervisor load from KSEG0. Any it fails shows what the R4600 reports.
